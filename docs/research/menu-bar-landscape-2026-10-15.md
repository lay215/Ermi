# macOS 菜单栏产品调研

调研日期：2026-10-15。范围：代表性产品的官方网页和官方仓库；未安装实测，不构成全市场统计。下文区分官方功能说明、仓库路线图与产品建议。版本与功能以访问时页面为准，不把官网宣传视为本机兼容性验证。

## 结论

“自己的 mac bar”至少包含三种不同目标：管理别人的菜单栏图标、在菜单栏提供自己的工具、制作屏幕顶部的聚合工作台。这三者可组合，但不能直接合并成首版范围。

现有代表产品已经覆盖图标整理、系统监控、日历会议、剪贴板、截图、防休眠和脚本扩展。用户通过三轮访谈确认图标整理与自有工具面板结合，首个模块为独立风扇控制；围绕个人使用与开源协作完善（2026-10-19 更新定位）。首版产品范围如下，技术实现与硬件兼容性仍待验证。

## 最终首版范围（用户已确认）

| 模块 | 首版行为 |
| --- | --- |
| 图标整理 | 常驻/折叠分组；独立展开栏，可访问被刘海遮挡的图标 |
| 工具面板 | 承载本 App 自有功能，首个模块为风扇监测与控制 |
| 独立控制 | 不依赖 Macs Fan Control，独立提供同类能力 |
| 自动温控 | 随温度自动调速；提供均衡、积极散热两种预设，默认选择均衡 |
| 固定转速 | 支持用户设置固定 RPM，保存为自定义预设 |
| 两点温控 | 支持设置开始提速温度及达到最高转速温度，中间自动调节 |
| 使用目标 | 满足个人使用，开放源码并支持社区协作 |

“默认均衡”指默认选择的 App 温控策略。是否在首次启动或登录时自动接管风扇未单独指定；建议首次由用户主动启用 App 控制，启用前保持系统自动。该建议是当前实现假设，不属于已确认的自动接管要求。

暂不纳入首版：多点温控曲线、按场景自动切换图标布局、日历/剪贴板/AI 等附加模块。没有承诺覆盖所有 Mac、固定降温幅度或发布渠道。

## 实施验收草案

以下将已确认需求转为后续验证条件，当前均未运行验证：

1. 用户可设置常驻/折叠图标，并从独立展开栏打开折叠或被刘海遮挡的原 App 菜单；不得只展示不可操作的图标。验证打开、关闭及再次访问的完整流程。
2. 风扇面板能显示真实设备的温度、当前 RPM 和当前控制模式；不能用模拟数据宣称硬件控制完成。
3. 用户可切换系统自动、App 自动温控和固定 RPM；显示的是请求状态还是已确认生效状态必须可区分。
4. 自定义固定 RPM 可保存、重新选择；输入边界依据已核实的设备能力确定。
5. 两点温控校验开始温度低于最高转速温度；验证低于起点、两点之间及高于终点时的行为。传感器来源、插值、平滑和参数范围以技术验证结果确定，不凭名称猜测。
6. 均衡和积极散热的参数及差异须有依据；在可比负载下记录温度、转速及噪声体验，不预先承诺降温数值。
7. 验证主动恢复系统自动、正常退出和禁用控制的行为；对进程异常、控制组件不可用、传感器失效与睡眠唤醒，专门验证控制状态及恢复路径。未证实前不得承诺崩溃会自动恢复。
8. 先在已探测本机验证独立读取及受控调速能力；其他机型与系统版本需分别验证。验证结果出来前不将产品范围等同于可实现性结论。

实施顺序建议：先验证本机风扇读写与恢复能力，再验证目标系统的图标管理和独立展开栏，最后整合面板与预设。当前任务交付为调研与需求文档，没有启动开发或改动风扇设置。

## 第一轮候选方向（保留调研对照）

| 方向 | 具体用户任务 | 首版候选边界 | 必须先回答的问题 |
| --- | --- | --- | --- |
| A. 图标整理器 | 找到被拥挤或刘海遮挡的已有图标 | 隐藏/展开、快捷键、明确的恢复入口 | 现有工具在哪个真实场景下无法满足？ |
| B. 个人状态与动作面板 | 快速查看自己关心的状态并执行下一步 | 单入口、少量摘要、一个核心动作、配置保存 | 每天最常看什么、做什么，数据从哪里来？ |
| C. 单点效率工具 | 缩短复制、入会、计时等某个高频流程 | 一个端到端场景、快捷入口、必要历史或设置 | 现有操作有哪一步最费事？ |
| D. 可扩展工具宿主 | 将不同脚本和服务做成统一入口 | 明确插件输入输出、刷新和失败状态 | 相比 SwiftBar/xbar，需要新增什么不可替代的价值？ |

在没有痛点证据前，建议优先考虑 B 或 C：先获得可持续使用的具体场景。若用户真正的问题是菜单栏图标管理，则 A 才应成为主方向。这个排序是产品判断，未经用户采纳。

PD 补充建议：若偏好开发工作状态面板，可考虑将有明确来源的构建、Agent 或任务状态与返回工作现场的动作结合；必须先验证所用工具的数据契约。OneNotch 已覆盖部分终端 Agent 跟踪，这不是未经竞争的空白方向。

## 对需求的约束

1. 菜单栏空间有限：常驻摘要、展开详情和提醒应分别考虑。聚合入口若需要多次翻找，也可能降低效率。
2. 增加模块不等于增加价值：日历、剪贴板、截图和 AI 各自已有成熟替代品，应先说明为什么需要在同一入口完成。
3. 原生系统也是替代方案：[Apple 菜单栏设置](https://support.apple.com/guide/mac-help/change-menu-bar-settings-mchlad96d366/mac)已提供菜单栏显隐和部分控制项配置；具体能力需与目标系统版本核对。
4. 如果后续选择图标管理，应专门验证目标系统、刘海/无刘海、多显示器、全屏和权限变化下的访问及恢复。当前没有做这些运行验证。
5. 如果后续选择服务状态聚合，应先验证数据来源、可获取字段、刷新频率和失效时的表达，再决定界面。没有证据时不承诺第三方额度、任务状态或 Agent 状态一定可取。

## 风扇控制补充调研与第二轮

一手来源：[产品说明](https://crystalidea.com/macs-fan-control)、[预设说明](https://crystalidea.com/macs-fan-control/fan-presets)、[命令行说明](https://crystalidea.com/macs-fan-control/command-line)。仅核实文档，没有执行风扇控制或修改现有 App。

- Macs Fan Control 公开功能包括转速与温度监测、系统自动模式、固定 RPM、基于温度传感器的控制；退出时恢复系统自动模式。
- 官方 CLI 文档列出启动最小化、日志、卸载等参数，没有列出设定 RPM 或切换预设的命令。本次未核实到可用于控制的公开接口，不等于证明所有外部集成途径都不存在。
- 调研区分“调用已安装的第三方软件”和“在自己的 App 中独立提供同类功能”；第二轮用户已选择后者。没有复用或嵌入第三方程序的决定。
- 本机只读探针：MacBookPro18,4、Apple M1 Max、macOS 27.0.1。该信息仅用于自用验证起点，不构成跨设备兼容承诺。

第二轮用户确认：

- 独立提供风扇控制，不依赖 Macs Fan Control。
- 希望减少电脑发热，自动控制风扇速度，并提供转速预设及自定义。
- 图标管理首版包含常驻/折叠分组、独立展开栏与访问刘海遮挡图标；场景自动布局未纳入已确认范围。

目标表述澄清：风扇主要改善散热，应以降低运行温度描述其作用；不能把它承诺为减少芯片产热。没有引入降功耗、限制性能或改动电源策略的需求。

第三轮用户确认：降温与噪声取舍按推荐，提供均衡和积极散热模式，默认均衡；自定义选择 A+B，即固定 RPM 和两点温控。访谈在本次产品范围内结束，无需额外确认已回答内容。

产品中区分系统自动和 App 自动温控，避免用户误判当前由谁控制。温控规则、传感器来源、可控转速边界与异常恢复均尚未实现或验证，不在访谈中凭空确定数值。
